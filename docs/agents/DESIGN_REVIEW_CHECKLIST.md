# Independent Design Review Checklist

実装開始前に、設計担当とは別のエージェント(別モデルまたは少なくとも別セッション)が使う設計レビュー用チェックリストです。
実装方法の細部ではなく、要件との整合性、責務境界、代替案、リスク、変更容易性を確認します。

設計担当の説明(「これで問題ないはずです」等)は主張であり、証拠ではありません。
レビュー担当は説明をそのまま採用せず、設計文書・Issue・要件を自分で読んで確認してください。
レビュー担当は指摘のみ行い、設計の書き直しは自分で行いません。修正は設計担当へ差し戻します。

## Requirements Alignment

- [ ] 解決したい問題と対象ユーザーが明確である
- [ ] Issueの受け入れ条件と設計が対応している
- [ ] 対象範囲と対象外が明記されている
- [ ] `VISION.md` / `REQUIREMENTS.md` と矛盾していない
- [ ] 重要な不明点が推測で埋められていない

## Design Quality

- [ ] 責務とモジュール境界が明確である
- [ ] 公開インターフェースが必要以上に広くない
- [ ] データの所有者とSingle Source of Truthが明確である
- [ ] 正常系、異常系、境界値、再実行、競合を考慮している
- [ ] 失敗時に安全側へ倒れる設計である
- [ ] 観測性、ログ、監査、復旧方法を考慮している
- [ ] 秘密情報・個人情報の保存、送信、ログ出力を考慮している

## Alternatives and Trade-offs

- [ ] 少なくとも現実的な代替案を1つ検討した
- [ ] 採用案の利点・欠点・将来コストが説明されている
- [ ] 新しい依存関係の必要性、保守性、ライセンスを確認した
- [ ] 可逆な判断と不可逆または高コストな判断を区別した
- [ ] 過剰設計になっていない

## ADR Decision

以下に該当する場合、ADRが必要か確認する。

- [ ] 外部依存・基盤・データストアを追加または変更する
- [ ] 公開API、永続化形式、認証・権限モデルを変更する
- [ ] 複数案から長期的なトレードオフを伴う判断をする
- [ ] 後から理由を説明する必要がある重要判断である
- [ ] ADRを作らない場合、その理由がIssueまたはPRに記録されている

## Implementation Readiness

- [ ] 実装を小さなIssueまたはPRへ分割できる
- [ ] テスト方針と完了の証拠が定義されている
- [ ] 移行、後方互換性、ロールバックの要否が明確である
- [ ] 実装担当が追加推測なしで着手できる
- [ ] 未解決事項と決定者が明確である

## Findings

各指摘には優先度を付ける。

- **Critical**: 安全性、重大なデータ損失、要件不成立など。設計承認不可。
- **High**: 実装前に解消すべき重大な欠陥。
- **Medium**: 解消が望ましいが、明示的に受容できるリスク。
- **Low**: 任意改善。承認を妨げない。

## Review Result

- Decision: **Approve / Fix first / Rethink**(blocking指摘 = Critical/Highの定義は `AGENTS.md` の「レビュー独立性」を参照)
  - `Approve`: blocking指摘(Critical/High)なし。実装着手可。
  - `Fix first`: blocking指摘があるが、設計方針自体は妥当。指摘を修正すれば承認できる。
  - `Rethink`: 設計方針自体に疑義があり、修正では済まない。要件整理まで差し戻す。
- ADR required: **Yes / No / Undecided**
- Blocking findings(Critical/High):
- Accepted residual risks:
- Reviewer:
- Review session or reference:

指摘がない場合は、無理に問題を作らず `Approve` と明記する。

設計が修正された場合、このレビュー結果は無効になる。修正後の設計を対象に再レビューし、新しいReview Resultを記録すること(古い`Approve`を使い回さない)。
