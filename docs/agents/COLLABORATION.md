# Claude × Codex Collaboration Guide

ClaudeとCodexを同じリポジトリで併用するための共通運用です。特定製品への依存を最小限にし、どちらが先に担当しても引き継げることを目的とします。

## 1. Single Source of Truth

- 共通ルールは `AGENTS.md` に一本化する。
- Claude固有の入口は `CLAUDE.md` とし、共通ルールを複製しない。
- 要件は `REQUIREMENTS.md`、設計は `ARCHITECTURE.md`、判断履歴は `docs/decisions/` に置く。
- 作業中の状態は `docs/agents/HANDOFF.md` に残す。
- チャット内だけに重要な判断を残さない。

## 2. 役割分担

役割は固定せず、Issueごとに決める。おすすめの基本形は次のとおり。

### パターンA: 設計、実装、レビューを分離

1. Claude: 要件整理、抜け漏れ確認、設計案比較
2. Codexまたは別セッション: 設計レビュー
3. 人間: 方針承認
4. Codex: Issue単位の実装、テスト、PR作成
5. Claudeの別セッションまたは第三の担当: 品質レビュー
6. Codex: 指摘修正

### パターンB: 実装とレビューを交代

1. 一方が実装
2. もう一方が、元の会話に依存せずIssueと差分だけからレビュー
3. 実装担当が修正

同じエージェントが設計、実装、最終承認を一人で完結しないことを推奨する。
設計レビューと品質レビューも、可能な限り別担当・別モデル・別セッションに分ける。やむを得ず同一担当が行う場合は、独立したコンテキストで再確認し、その理由と残余リスクをIssueまたはPRに記録する。

## 3. 同時編集の制限

- 1 Issue = 1担当エージェント = 1ブランチを基本とする。
- 同じファイルをClaudeとCodexが同時に変更しない。
- 並行作業は、Issueと変更領域が独立している場合だけ行う。
- 担当交代時は、コミットまたは明確な差分状態を残してから引き継ぐ。
- 未コミット変更がある状態で別エージェントに書き込みを許可しない。

## 4. 引き継ぎルール

担当者は終了前に `HANDOFF.md` を更新する。
次担当者は、作業を始める前に次を確認する。

1. Issueと受け入れ条件
2. 現在のブランチと差分
3. 変更済みファイル
4. 実行済みの検証
5. 未解決事項
6. やってはいけない変更

口頭の「だいたい終わった」は引き継ぎ完了とみなさない。

## 5. レビューの独立性

レビューの原則(完了報告の扱い、独立確認、Approve/Fix first/Rethink等)は `AGENTS.md` の「レビュー独立性」を正とする。本節はルールを再掲せず、Claude×Codex運用に固有の実務手順のみを補足する。

- 設計レビュー担当は `docs/agents/DESIGN_REVIEW_CHECKLIST.md`、品質レビュー担当は `docs/agents/REVIEW_CHECKLIST.md` を使う。
- 「別モデルまたは別セッション」の実務上の組み方は、`## 2. 役割分担` のパターンA・パターンBを基本とする。ClaudeとCodexで担当を分ける、または同一製品でも会話セッションを分けて「元の会話に依存せずIssueと差分だけからレビューする」。
- レビュー担当は、Issueの受け入れ条件・要件文書・設計文書との整合性、エラー処理や境界値の抜け、不要な変更の混入、テストが挙動を検証しているか、失敗時に安全側へ倒れるかを確認する(具体的な確認観点は使用するチェックリストに従う)。
- レビュー結果(Approve / Fix first / Rethink)は、チェックリストの `Review Result` に記録するだけでなく、PRのコメントまたは本文にも残し、`docs/agents/HANDOFF.md` の担当交代時に参照できるようにする。

## 6. 完了の定義

エージェントの自己申告ではなく、リポジトリに残る証拠で判断する。自己申告(完了報告)自体は証拠に含まない(詳細は `AGENTS.md` の「レビュー独立性」)。

- CI green
- 受け入れ条件の確認結果
- テスト結果
- PRレビュー結果
- 必要な文書更新
- HANDOFFの更新

これらは品質の証拠であり、完全性の証明ではない。
